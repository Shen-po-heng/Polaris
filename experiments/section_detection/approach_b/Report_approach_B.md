## What Are the 4 Indicators?

Before diving into results, here is what each metric actually measures — and what kind of mistakes it catches.

### Precision — "When we say it's a section, how often are we right?"

$$\text{Precision} = \frac{\text{True Positives}}{\text{True Positives} + \text{False Positives}}$$

**Catches**: False alarms — detecting something as a section header when it is not.

**Example**: If the detector flags a figure caption ("Figure 3. Training curves...") as a section header, that's a False Positive. Precision would drop.

**Our result (80.0%)**: In 5 of our 25 detections, we reported a section that didn't exist in the ground truth — mainly due to sub-headings and figure labels being picked up as sections on some pages.

---

### Recall — "Of all the real sections, how many did we find?"

$$\text{Recall} = \frac{\text{True Positives}}{\text{True Positives} + \text{False Negatives}}$$

**Catches**: Misses — real sections that were never detected.

**Example**: If the paper has a "Methods" section and the detector never finds it, that is a False Negative. Recall would drop.

**Our result (55.6%)**: We found only about half of all ground-truth sections across 5 papers. The main cause: section headings with the same font size as body text (so the font-size heuristic doesn't trigger) and totally broken text extraction in one paper (Adam).

---

### F1 Score — "Overall quality, balancing both mistakes"

$$\text{F1} = \frac{2 \times \text{Precision} \times \text{Recall}}{\text{Precision} + \text{Recall}}$$

**Catches**: Neither extreme is acceptable. A detector that always says "no sections" has perfect precision (never wrong) but zero recall. A detector that flags every line as a section has perfect recall but near-zero precision. F1 penalises both.

**Example**:
- Precision 100%, Recall 10% → F1 = 18% (useless, misses everything)
- Precision 50%, Recall 90% → F1 = 64% (lots of noise, but finds most sections)
- Precision 100%, Recall 88% → F1 = 94% (what Transformer achieved)

**Our result (64.3%)**: Strongly skewed by the Adam failure (F1 = 0%). Excluding Adam: mean F1 = **80.5%**.

---

### Type Accuracy — "When we find a section, is its category right?"

$$\text{Type Accuracy} = \frac{\text{Correctly typed sections}}{\text{All detected sections that match ground truth}}$$

This measures only the **classification quality** of sections we already found. It answers: did we correctly label it as `introduction` vs `method` vs `results`?

**Example**: Detecting "2 Background" as `introduction` instead of `related_work` is a type error. The section was found, but mis-categorised.

**Our result (77.5%)**: The one mis-classification was "2 Background" in Transformer (labelled `introduction` instead of `related_work`). This is an inherent ambiguity — "Background" sections appear in both positions in real papers. Type accuracy was 100% for all other papers.

## Approach B: How It Works

```
PDF → pdfplumber (character extraction)
    → group chars into lines by y-coordinate
    → compute body font size (median of all chars)
    → per line:
         normalize text (insert spaces at word boundaries)
         regex match → section type
         font check (is_larger OR is_bold)
         if both pass → DetectedSection
```

**Key design choice**: Two-gate system. A line must pass both (a) regex pattern match and (b) font size/bold heuristic to be accepted as a section header. This maximises precision at the cost of recall.

## Bugs Encountered and Fixes

### Bug 1 — No space tokens between words

**Symptom**: `'PublishedasaconferencepaperatICLR2015'`, `'WeintroduceAdam...'`

**Root cause**: arXiv PDFs generated by LaTeX store character positions, not space characters. Word gaps are visual (character spacing), not encoded as space glyphs. `pdfplumber` joins all characters in a line without inserting spaces.

**Impact**: Body text becomes unreadable noise, but more critically, section headings like `'1Introduction'`, `'2Background'`, `'3ModelArchitecture'` also lose their spaces. Regex patterns like `\d+\.?\s+introduction` require whitespace → no match.

**Fix**: Added `_normalize_heading()` that runs before regex matching:
```python
text = re.sub(r"(\d)([A-Za-z])", r"\1 \2", text)   # "1Introduction" → "1 Introduction"
text = re.sub(r"(\.)([A-Z])",    r"\1 \2", text)    # "1.Introduction" → "1. Introduction"
text = re.sub(r"([a-z])([A-Z])", r"\1 \2", text)    # "RelatedWork" → "Related Work"
```

**Effect**: Recall jumped from ~20% to 50–89% on 4 of 5 papers.

---

### Bug 2 — Benchmark normaliser wrong order of operations

**Symptom**: Detected section `"2RelatedWork"` stored as `"2RelatedWork"`, ground truth `"2 Related Work"`. Benchmark reported them as EXTRA + MISSED (non-matching) instead of a correct match.

**Root cause**: `_normalize()` in benchmark.py applied `.lower()` first, then the camelCase rule `([a-z])([A-Z])`. After lowercasing, there are no more uppercase letters → rule never fires → `"2relatedwork"` ≠ `"2 related work"`.

**Fix**: Run space-insertion rules BEFORE lowercasing:
```python
def _normalize(s):
    s = s.strip()
    s = re.sub(r"(\d)([A-Za-z])", r"\1 \2", s)  # must be before .lower()
    s = re.sub(r"(\.)([A-Z])",    r"\1 \2", s)
    s = re.sub(r"([a-z])([A-Z])", r"\1 \2", s)  # must be before .lower()
    return re.sub(r"\s+", " ", s.lower()).strip()
```

---

### Bug 3 — Unicode ligature mismatch

**Symptom**: AlexNet EXTRA contained `"4 reducing overﬁtting"` (with `ﬁ` = U+FB01) while ground truth had `"4 reducing overfitting"` (with `fi` = two ASCII chars). Counted as a false positive + a miss simultaneously.

**Root cause**: Academic PDFs use Unicode ligature glyphs (ﬁ, ﬂ, ﬀ, ﬃ, ﬄ) for common letter pairs. These appear as single characters in extracted text. Ground truth was typed with normal ASCII.

**Fix**: Added ligature normalisation as the first step in `_normalize()`:
```python
_LIGATURES = str.maketrans({"ﬁ": "fi", "ﬂ": "fl", "ﬀ": "ff", "ﬃ": "ffi", "ﬄ": "ffl"})
s = s.translate(_LIGATURES)
```

**Effect**: AlexNet F1 jumped from 82.4% → 94.1%.

---

### Bug 4 — Windows cp950 UnicodeEncodeError

**Symptom**: `UnicodeEncodeError: 'cp950' codec can't encode character '∗'` (asterisk operator used in Adam paper's footnote marker), crashing benchmark output mid-run.

**Root cause**: Windows Terminal defaults to code page 950 (Traditional Chinese Big5). Unicode characters outside that range (mathematical symbols, ligatures, etc.) cannot be printed directly.

**Fix**: Force UTF-8 output at the top of each script:
```python
import io, sys
if hasattr(sys.stdout, "buffer"):
    sys.stdout = io.TextIOWrapper(sys.stdout.buffer, encoding="utf-8", errors="replace")
```

---

### Bug 5 — Adam v9: Drop cap rendering completely breaks detection

**Symptom**: Adam paper scored 0% on all metrics. Even `abstract` and `references` (which bypass font checks in the code) were not detected.

**Root cause**: The Adam v9 PDF uses decorative drop caps for section headings:
- `"A"` (font size 11.6, rendered large) + `"BSTRACT"` (font size 9.3) → pdfplumber groups them as **two separate lines** → neither matches `^\s*abstract\s*$`
- `"1I"` + `"NTRODUCTION"` → section number and first letter fused, remainder on next line

Additionally, the entire document has no space tokens — even the title is `'A:AMSO'` + `'DAMETHODFORTOCHASTICPTIMIZATION'` (garbled due to character reordering in the PDF stream).

**Status**: No fix applied. This is an inherent limitation of character-extraction approaches on PDFs with unusual typesetting. Requires a layout-aware parser (GROBID) or OCR-based approach.

---

### Bug 6 — arXiv timestamp watermark pollutes line grouping

**Symptom**: Pages contain dozens of single-character lines: `'2'`, `'0'`, `'2'`, `'2'`, `'g'`, `'u'`, `'r'` etc. interspersed between content lines.

**Root cause**: arXiv adds a rotated timestamp watermark (e.g., `"arXiv:1706.03762v7 [cs.CL] 2 Aug 2023"`) along the page margin. Each character of this rotated text appears at a different y-coordinate → `_group_chars_by_line` creates one single-character "line" per character.

**Impact**: These do not trigger section detection (too short, no regex match), but they increase noise in line grouping and can occasionally merge with nearby content.

**Status**: Mitigated. Single-char lines don't match any regex pattern and are filtered implicitly. No explicit fix needed for this experiment, but worth noting for downstream text extraction.

## Conclusions

### What works well
- **Precision is near-perfect** (100% excluding Adam): when the detector fires, it is almost always correct. The two-gate system (regex + font heuristic) prevents false alarms effectively.
- **Two-column layout (AlexNet) works surprisingly well** (94.1% F1): section headings in NIPS-format papers tend to use larger fonts and span the full column width, making them easier to detect than in some single-column papers.
- **Type classification is reliable** (97% when section is detected): the regex patterns correctly identify section roles with minimal ambiguity.

### What does not work
- **Adam v9 is completely broken** due to drop cap rendering and no word-space tokens. This PDF would require GROBID (Approach A) or OCR.
- **Same-size headings are invisible**: when a paper uses the same font size for headings as body text (common in CVPR-style papers like ResNet), the font heuristic fails entirely. Recall drops to 50%.
- **Non-generic section names** ("3 BERT", "4 Why Self-Attention") cannot be matched by general regex patterns without domain-specific rules — which defeats the purpose of a general-purpose extractor.

### Implication for GraphRAG
Approach B is **usable as a best-effort layer** for standard arXiv papers, but it cannot be the sole section detector in a production GraphRAG system. One mis-detected section propagates to a wrong entity type in the knowledge graph. A 50% recall means half the paper's sections carry no section context at all.

**Approach A (GROBID) is strongly motivated** by:
1. The Adam v9 failure (drop cap PDFs are not rare)
2. The font-size failure mode (one third of our test papers)
3. GROBID's training-based approach handles both cases natively
